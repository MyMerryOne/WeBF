# Capture Package Contract

This document describes the technical contract for packages generated by WeBF. It is an implementation and independent-verification reference; it does not determine legal admissibility, authorship, completeness, or the current qualified status of a timestamp service.

## Current schema

New packages use manifest schema `1.1` and identify the tool as `WeBF-CaptureVerification`. The manifest is UTF-8 JSON and records the target and final URLs, capture timing, operator metadata, jurisdiction, network observations, artifact hashes, package-member inventory, timestamp endpoint, provenance, signature state, and stated limitations.

The primary captured artifact is `capture/page.warc.gz`. Screenshots, rendered HTML, PDFs, raw HTTP bytes, legal-page material, and network files are supporting artifacts. Browser-derived files are not substitutes for the WARC or raw response bytes.

## ZIP members

Every generated package contains these members:

```text
manifest.json
manifest.sha256
package_hashes.json
package_hashes.sha256
VERIFICATION.md
report/capture_report.html
report/capture_report.pdf
network/dns.json
network/whois.txt
network/tls_certificate.json
timestamp/request.tsq
timestamp/response.tsr
timestamp/timestamp_info.json
timestamp/verify.sh
timestamp/verify.ps1
capture/page.warc.gz
capture/http_response_raw.bin
```

The following members are conditional:

- `capture/screenshot_full.png`, `capture/screenshot_viewport.png`, `capture/page.html`, and `capture/page.pdf` require browser capture. They are omitted with `--no-browser` or when browser rendering fails.
- `capture/legal/` and `capture/legal/legal_index.json` are present only when legal content is discovered and captured. Use `--no-legal` to skip discovery.
- `timestamp/tsa_trust.pem` and `timestamp/tsa_untrusted.pem` are included when trust material is supplied. Italian captures require both files before capture begins.

The manifest `package_members` list is the authoritative inventory for schema `1.1`. A verifier must reject missing declared members, unexpected members, duplicate names, unsafe paths, malformed JSON, invalid hash lengths, and missing required primary evidence.

## Hash relationships

`manifest.sha256` is a detached SHA-256 digest of the exact `manifest.json` bytes. The manifest contains SHA-256 and SHA-512 values for captured artifacts.

`package_hashes.json` contains SHA-256 and SHA-512 values for every other ZIP member, including `manifest.json`, reports, scripts, timestamp material, and network data. `package_hashes.sha256` is a detached SHA-256 digest of the exact package-hash index bytes. The index is a secondary comparison mechanism and is not itself included in the RFC 3161 manifest imprint; an external signature or second trusted binding is required when the index must be independently trusted against an attacker who can replace both the index and a member.

## Timestamp verification layers

WeBF records an RFC 3161 request and response for the manifest hash. Verification has separate layers:

1. The built-in verifier checks the timestamp response status and confirms that the token imprint and nonce correspond to the exact `manifest.json` bytes.
2. `timestamp/verify.sh` or `timestamp/verify.ps1` can validate the signer certificate chain using the supplied trust anchor and intermediate material.
3. Current revocation, service identity, and qualified-service status require an independent validation record against the applicable Trusted List. They are not inferred from a URL, provider name, token signer, or successful local chain check.

If timestamp material is missing, empty, or invalid, verification must fail or report the corresponding unavailable/failed status. A timestamp failure does not turn an incomplete package into a valid complete package.

## Verification and failure behavior

Independent verification should:

1. Validate the manifest structure and schema version.
2. Compare the ZIP inventory with `package_members`.
3. Verify detached manifest and package-index digests.
4. Recompute artifact and package-member hashes.
5. Confirm that the primary WARC exists and is bound to the manifest.
6. Check timestamp material and RFC 3161 imprint/nonce relationships.

Any failed required check produces a non-zero verification result. A valid hash proves only that the checked bytes match the recorded digest. It does not prove that the content is true, complete, authored by the operator, lawfully collected, or legally admissible.

## Historical packages

Repository captures produced before the schema and terminology migration may contain schema `1.0`, the former tool name, different report labels, or a smaller package inventory. They are historical evidence and must remain byte-for-byte unchanged. Do not upgrade them in place; create a new package or superseding report with clear provenance when a correction is necessary.
